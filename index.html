OO design metrics priority 1

C&K is the most popular OO suite: WMC, DIT, NOC, CBO, RFC, LCOM. Li’s suite fixes some C&K limits: NAC, NDC, NLM, CMC, CTA, CTM.

File 04 · Chidamber & Kemerer (1994) + Li (1998)

WMC · Weighted Methods per Class ↓ good
WMC=∑i=1nci

ci = complexity of method Mi. If every ci = 1, then WMC = n (the number of methods).

Viewpoints: more methods and more complex methods mean more time and effort to develop and maintain · more impact on children (they inherit all methods) · large classes are application-specific, so less reuse.

Inheritance metrics: DIT, NOC, NAC, NDC

DIT · Depth of Inheritance Tree

Depth of the class in the tree. Root = 0. With multiple inheritance, take the maximum length from the node to the root.

Deeper → inherits more methods, harder to predict behaviour · more design complexity · but more reuse of inherited methods.

NOC · Number of Children

Number of immediate subclasses only.

More children → more reuse · higher chance of improper abstraction of the parent (misuse of subclassing) · more influence on the design, so it needs more testing.

Li’s criticism → new metrics

DIT has two ambiguities:

  • Unclear with multiple inheritance and multiple roots (in the slide’s Fig. b, is DIT(B) 1 or 2?).
  • DIT claims to count classes that can affect a class, but in Fig. a, DIT(A) = DIT(B) = 2 even though B inherits from more classes.

Fix → NAC: total number of ancestor classes (unit: class).

NOC counts only immediate subclasses, but a class influences all its subclasses.

Fix → NDC: total number of descendant classes (unit: class).

WMC mixes two independent things (method count and method complexity). Fix → NLM (count, unit: method) + CMC (sum of complexity, unit: same as the complexity measure, e.g. LOC or McCabe paths).

  • A root has DIT = 0 and NAC = 0. A leaf has NOC = 0 and NDC = 0.
  • DIT(C) uses the longest path (C→K→J = 2), but NAC(C) counts every ancestor (A, K, J = 3).
  • NOC(J) = 1 (only K) but NDC(J) = 5 (K, C, G, H, I).

Coupling metrics

CBO · Coupling Between Object classes ↓ good

Number of classes coupled to this class. Coupled = one calls the other’s methods or uses its variables. Count both directions. It is a set: if A uses B and B uses A, B counts once. Coupling can come from method calls, field access, inheritance, arguments and return types. Unit: class.

High CBO → harms modularity, prevents reuse · more sensitive to changes, so maintenance is harder · testing must be more rigorous.

Slide “CBO Example”: C extends SuperC and uses aSC1, mSC1(); C calls b.mB1(), b.mB2(); A calls c.mC1() → CBO(C) = {SuperC, B, A} = 3 (B counted once although it is called 3 times).

RFC · Response For a Class ↓ good
RS=M∪RRFC=|RS|

M = all methods of the class. R = all methods called by those methods. It is a set: each called method counts once, however many times it is called.

High RFC → testing and debugging harder (tester needs more understanding) · more complex class · the worst-case value helps plan testing time.

Slide RFC example 2 (left case): A.m1→B.m1, B.m2 · A.m2→C.m1 · A.m3→D.m1, D.m2 · A.m4 calls nothing.
RS = {A.m1..A.m4, B.m1, B.m2, C.m1, D.m1, D.m2} → RFC = 9.

Right case: A.m1→B.m2 · A.m2→C.m1 · A.m3→A.m4.
R = {B.m2, C.m1, A.m4}, but A.m4 is already in M → RS = {A.m1..A.m4, B.m2, C.m1} → RFC = 6.

A call to the class’s own method adds nothing (it is already in M). Union, not sum.

CTA · Coupling Through Abstract data type

Number of classes used as types in the attribute declarations of the class. Also called DAC (data abstraction coupling).

class A { int a; ... };      // CTA(A) = 0
class B { A anA; ... };    // CTA(B) = 1
CTM · Coupling Through Message passing

Number of different messages sent from the class to other classes, excluding messages to objects created locally inside its methods. Also called MPC.

class A { void A1(B* b){ b->B1(); } };
// CTM(A) = 1, CTM(B) = 0

Li: a class can be coupled in 3 forms: inheritance, abstract data type (CTA), message passing (CTM).

Other coupling metrics (Al Dallal, 2015)

  • CBO, RFC, CTA/DAC, CTM/MPC (above).
  • CBO_U: classes (excluding inherited ones) that are used by the methods of the class.
  • CBO_IUB: classes (excluding inherited ones) that use the attributes or methods of the class.
  • OCMEC: distinct classes used as parameter types of the class’s methods.

File 04 · Coupling and cohesion metrics

LCOM (C&K), also called LCOM2 ↓ good
P={(Ii,Ij)|Ii∩Ij=∅}Q={(Ii,Ij)|Ii∩Ij≠∅}
LCOM={|P|−|Q|if |P| > |Q|0otherwise

Same as max(|P| − |Q|, 0).

Iⱼ = set of instance variables used by method Mⱼ. If all sets are empty, P = ∅.

Example above: Q = {(m1,m2)} = 1, P = the other 5 pairs → LCOM2 = 5 − 1 = 4.

Slide example 1: I1 = {a,b,c,d,e}, I2 = {a,b,e}, I3 = {x,y,z} → P = {(M1,M3),(M2,M3)} = 2, Q = {(M1,M2)} = 1 → LCOM2 = max(2−1, 0) = 1.

Viewpoints: cohesion is good (promotes encapsulation) · lack of cohesion → split the class into two or more · low cohesion raises complexity and the chance of errors.

LCOM1 (from the Al Dallal table) = number of pairs that share nothing = |P| (here 5).

“Do you see any problem?” LCOM2 is cut at 0, so many different classes all get 0. Slide: when m1 also uses c, Q = 3, P = 0 → 0; the earlier version with Q = 2, P = 1 also gives 0. LCOM2 cannot tell these classes apart.

LCOM3 · Li & Henry 1993 ↓

Graph: each method = node. Edge when two methods share ≥ 1 attribute.

LCOM3 = number of disjoint components

Example: {m1,m2}, {m3}, {m4} → 3.

LCOM4 · Hitz & Montazeri 1995 ↓

Same graph as LCOM3, plus an edge when one method calls the other.

LCOM4 = number of disjoint components

m2–m3 and m4–m3 calls join everything → 1.

LCOM5 · Henderson-Sellers 1996 ↓
LCOM5=m−∑i=1ap(Ai)am−1

p(a1) = 2, p(a2) = p(a3) = p(a4) = 1 → Σ = 5.

LCOM5 = (4 − 5/4) / (4 − 1) = 2.75 / 3 = 11/12

Coh · Briand et al. 1998 ↑ good
Coh=∑i=1ap(Ai)m·a

Same Σ = 5 → Coh = 5 / (4 · 4) = 5/16

Meaning: the fraction of the m × a method–attribute grid that is actually used.

Shortcut: Σp(Aᵢ) = total number of method→attribute lines = Σ|Iᵢ|. Just count the lines in the picture. Calls do not count for LCOM5 or Coh.
TCC · Tight Class Cohesion (Bieman & Kang 1995) ↑ good
TCC=directly connected pairstotal pairstotal pairs=m(m−1)2

Two methods are directly connected if they are directly connected to the same attribute. A method is directly connected to an attribute when the attribute appears in its body or in the body of a method it invokes (directly or transitively).

Example above: m2 calls m3, so m2 also “uses” a3. m4 calls m3, so m4 also uses a3. Expanded sets: m1{a1,a2}, m2{a1,a3}, m3{a3}, m4{a4,a3}.
Connected pairs: (m1,m2) a1 · (m2,m3) a3 · (m3,m4) a3 · (m2,m4) a3 → TCC = 4/6.

LCC · Loose Class Cohesion (Bieman & Kang 1995) ↑ good
LCC=directly + indirectly connected pairstotal pairs

m (connected to attribute j) is indirectly connected to attribute i when some method X is connected to both i and j. In graph words: pairs in the same connected component of the TCC graph.

CC · Class Cohesion (Bonja & Kidanmariam 2006) ↑ good
Sim(mi,mj)=|Ii∩Ij||Ii∪Ij|CC=∑Sim (all pairs)total pairs

Use the raw attribute sets (no calls). Example: Sim(m1,m2) = |{a1}| / |{a1,a2}| = 1/2. Others: (m1,m3) 0/3, (m1,m4) 0/3, (m2,m3) 0/2, (m2,m4) 0/2, (m3,m4) 0/2.

CC = (1/2) / 6 = 1/12

Package-level metrics short file, sure marks

File 07 · Robert Martin

Package cohesion ↑ good
Cohesion=actual class couplingsn(n−1)

n = number of classes in the package. Range 0 (minimum) to 1 (maximum).

Slide: n = 5, 6 relationships → 6 / (5 × 4) = 0.3

Ca · Afferent couplings = fan-in

Number of classes outside this package that depend on classes inside it.

Memory: Afferent = Arriving.

Ce · Efferent couplings = fan-out

Number of classes inside this package that depend on classes outside it.

Memory: Efferent = Exiting.

Instability I
I=CeCa+Ce

I = 0 → completely stable  ·  I = 1 → completely unstable

Stability here is not about how often the package changes. It is about the work needed to make a change. Many packages depend on it → changing it means fixing all of them → stable (hard to change). It is an indicator of the package’s resilience to change.

  • Ca and Ce count classes, not arrows. One class with 3 outgoing arrows adds only 1 to Ce.
  • I = Ce on top (efferent). Swapping Ca and Ce is the classic mistake.
  • Dashed arrows between packages show package dependencies. Class-level arrows (inheritance, association) show how they are implemented. Count from the class arrows.

Refactoring priority 1

File 06 · Fowler, refactoring.guru

Code smells

Not bugs. Violations of design fundamentals that lower code quality. Fowler: “a surface indication that usually corresponds to a deeper problem.” Smells can indicate technical debt.

Technical debt

The cost of extra work caused by choosing a quick, easy solution now instead of a better one that takes longer. Example: skipping tests speeds you up now, but slows you every day until you pay the debt by writing the tests.

Causes: business pressure · not understanding the consequences of debt · delayed refactoring (new code keeps depending on obsolete parts, so more must be reworked later).

What is refactoring?

  • Kent Beck: a change that leaves behaviour unchanged but improves a non-functional quality (simplicity, flexibility, understandability).
  • Fowler: changing a system so it does not alter external behaviour but improves internal structure.
  • Fowler: a disciplined way to clean up code that minimises the chance of introducing bugs.
  • Fits agile well, but can and should be used with other processes too.

The common smells

Duplicated code

Same or very similar code in many places. Believed to be the worst smell: a bug fix may not reach every copy; code is bigger than needed. Slide caption: missing inheritance or delegation.

→ Extract Method

Long method

Too many lines. Over 20 is usually bad, under 10 usually good, no hard rule. Longer = harder to understand, change, reuse. Slide caption: missing inheritance or delegation.

→ Extract Method

Long parameter list

Too many parameters. Pass enough so the method can get what it needs, not everything (an object is missing).

→ Introduce Parameter Object · Preserve Whole Object

Large class

Does too much: many attributes, many methods. Abstraction fault (more than one concern, or methods that belong elsewhere). Often comes with duplicated code.

→ Extract Class · Move Method

Shotgun surgery

One small change forces many small changes in many classes. Opposite of divergent change.

→ Move Method / Move Field · Inline Class

Feature envy

A method uses mostly another class’s data and methods. It was put in the wrong class: data and the actions on it should live together.

→ Move Method (to the class it uses most)

Data class

Only fields with getters and setters, nothing else. A data holder. Other classes usually have feature-envy methods that should move here.

→ Move Method (move behaviour in)

Lazy class

A class that does too little to justify existing.

→ Inline Class · Collapse Hierarchy

Wear one hat at a time

  • Coding: add new capabilities.
  • Testing: perform testing, add test cases.
  • Refactoring: restructure code. Adds no new features, adds no tests (may modify some).

Swap hats often, but wear only one at a time.

Why refactor?

  • Improve design → easier to change.
  • Easier to understand (“write for people, not the compiler”).
  • Help find bugs (refactor while debugging).
  • Clean code.

Clean code is…

  • obvious to other programmers
  • free of duplication
  • passing all tests
  • minimal in classes and moving parts (less code = less maintenance, fewer bugs)

Fowler: “Any fool can write code that a computer can understand. Good programmers write code that humans can understand.”

Should we refactor?

Yes. Getting the design right the first time is very hard, the original design is often inadequate, and requirements are often not understood.

When to refactor

  • When adding a feature
  • When fixing a bug
  • During a code review (best in a pair with the author)

Ward Cunningham: “Unfinished refactoring is like going into debt.”

When NOT to refactor

  • Close deadlines
  • Prematurely published interfaces
  • Unstable, rubbish code

Refactoring activities (Mens & Tourwé)

Identify where to refactor (code smells)
Decide which refactoring(s) to apply
Guarantee behaviour is preserved
Apply the refactoring(s)
Assess the effect on design quality
Keep other artifacts consistent (docs, design, tests)

Key to safe, predictable refactoring: go step by step and run tests after each change.

Creating your own refactoring: consider a change → check it does not change external behaviour → break it into small steps (points where you can compile and test) → do it and note what you do → do it again and refine the notes → after 2–3 times you have a workable refactoring.

The core refactorings, before → after

Extract Method (one of the most common)

A fragment can be grouped → make it a method whose name explains its purpose.

Before
void printOwing(double amount) {
  printBanner();
  //print details
  WriteLine("name:" + _name);
  WriteLine("amount" + amount);
}
After
void printOwing(double amount) {
  printBanner();
  printDetails(amount);
}
void printDetails(double amount) {
  WriteLine("name:" + _name);
  WriteLine("amount" + amount);
}
Create a method named after the intention
Copy the extracted code
Handle local variables / parameters: make them a parameter, a return value, or declare inside
Compile
Replace the fragment with a call
Compile and test

Inline Method (opposite of Extract Method)

The body is as clear as the name → put the body into the callers and remove the method.

Before
int getRating() {
  return moreThanFiveLateDeliveries() ? 2 : 1;
}
boolean moreThanFiveLateDeliveries() {
  return numberOfLateDeliveries > 5;
}
After
int getRating() {
  return numberOfLateDeliveries > 5 ? 2 : 1;
}

Replace Temp with Query

A temp variable holds the result of an expression → extract the expression into a method, replace every use of the temp with the call. Other methods can now reuse it.

Before
double calculateTotal() {
  double basePrice = quantity * itemPrice;
  if (basePrice > 1000) return basePrice * 0.95;
  else return basePrice * 0.98;
}
After
double calculateTotal() {
  if (basePrice() > 1000) return basePrice() * 0.95;
  else return basePrice() * 0.98;
}
double basePrice() { return quantity * itemPrice; }
Find a temp assigned once
Extract the right-hand side into a method
Replace all references to the temp
Remove the temp’s declaration and assignment
Compile and test

Move Method

A method uses (or is used by) more features of another class than its own → create it in the class it uses most; turn the old one into a simple delegation or remove it.

Extract Class

One class does the work of two → create a new class and move the related fields and methods into it.

Obstacles to refactoring

  • Complexity: changing design and understanding code are hard
  • Possibility of introducing errors: run and build tests
  • Cultural issues: “We pay you to add features, not to improve code!”
  • Performance: refactoring may slow execution
  • Time pressure: refactoring takes time; better after delivery

Model refactoring

Refactoring at a higher abstraction level (UML), integrated into model-driven development.

Advantages: eases visualization (easier smell detection) · higher efficiency (coarser granularity) · language independence · reduces complexity (code generation hides accidental complexity).

Class diagrams: over 60% of Fowler’s refactorings are shown with them. Kinds: addition, removal, move, generalization, specialization (e.g. Lecture + Seminar → pull title into Course).

State machine diagrams: group states, fold/unfold outgoing transitions, move state into/out of composite.

Refactoring to patterns: e.g. Extract Composite (subclasses implement the same Composite → extract a superclass that does it).

Tools: IntelliJ IDEA, Eclipse, NetBeans, JRefactory, jFactor, RefactorIT, Xrefactory. Research: refactoring detection, correction, prioritization.

Ch 1 · Measurement: what and why

File 01

Definition

Measurement = assigning numbers or symbols to attributes of entities in the real world, by clearly defined rules.

Entity = an object (person, room, class, car) or an event (journey, testing phase). Attribute = a property of an entity (area, colour, cost, size, complexity, number of wheels).

Direct vs indirect (calculation)

MeasureType
Distance (km)Direct
Speed (km/h)Indirect
Productivity (LOC/h)Indirect
Program size (no. classes)Direct
Defect density (bugs/KLOC)Indirect

Rule: a division of two measures (x per y) is indirect. Other indirect examples: soccer league points, an organization’s ability to produce good software.

Key quotes

  • Galileo: “What is not measurable make measurable.”
  • Tom DeMarco: “You cannot control what you cannot measure.”
  • Gilb’s Principle of Fuzzy Targets: projects without clear goals will not achieve their goals clearly (e.g. “the product will be user friendly”).

Accuracy depends on the instrument and the definition. Even good instruments leave margin for error (shoes on when measuring height?). The scale must suit the purpose (height in cm, not km).

Why measure: understand → control → improve

Understand: assess what happens now; set baselines for future goals
Control: use baselines and goals to predict, then change process/product to meet goals
Improve: e.g. more design reviews based on measured specification quality

Every measurement must be motivated by a clear goal. Goals tell us how the data will be used.

Managers ask: cost of each process? staff productivity? code quality? will users be satisfied? how to improve?

Engineers ask: are requirements testable? found all faults? met product/process goals? what will happen in future?

Who measures: developers (requirements consistent and complete? design quality? code ready for testing?) · managers (delivery date, budget) · customers (meets requirements? enough quality?) · maintainers (what to upgrade).

Scope of software metrics: quality models and measures (e.g. use → factor → criteria → metrics: product operation = usability, reliability, efficiency; product revision = reusability, maintainability, portability, testability) · reliability models (part of most quality models) · security metrics · structural and complexity metrics · capability maturity assessment · management by metrics · evaluation of methods and tools.

Summary: without measurement you cannot tell if process/product is improving · metrics set meaningful goals and a baseline · they find causes of defects · on a product they show which requirements may change, which modules are error-prone, how much testing each module needs.

Representational theory

Data must represent the attribute, and manipulating the data must preserve the relationships we observe among entities.

Empirical relation = relationship among real-world entities: unary (A is tall), binary (A taller than B), ternary (A on B’s shoulders is taller than C).

Measurement = the mapping from the empirical world to the formal (numeric) world. Measure = the number or symbol assigned to the entity.

Some empirical relations are not agreed yet (personal preference: which meal is tastier) → rating formats.

Representation condition

Mapping M must map entities to numbers and empirical relations to numerical relations so that they preserve each other both ways (“if and only if”).

Empirical relationNumerical relation
A taller than BM(A) > M(B)
A is tallM(A) > 70
A much taller than BM(A) > M(B) + 15
A higher than B if sitting on C’s shoulders0.7 M(A) + 0.8 M(C) > M(B)

Valid mapping: Wonderman 72, Frankie 84, Peter 42. Checks: 84 > 72 · 72 > 70 · 84 > 42+15 = 57 · 72 > 57 · 0.7(42) + 0.8(72) = 87 > 84 ✓.

Invalid mapping: Peter = 60. Then Peter + 15 = 75 and Wonderman 72 > 75 is false, but Wonderman is much taller than Peter → “much taller than” breaks.

Key stages of formal measurement

Identify the attribute for some real-world entities
Identify empirical relations for the attribute
Identify numerical relations for each empirical relation
Define the mapping from entities to numbers
Check numerical relations preserve and are preserved by empirical ones (representation condition)

Failure criticality example: 3 classes (delayed response, incorrect output, data loss). With only class membership any 3 different numbers work (6, 4, 69). After learning data loss > incorrect output > delayed response, M must satisfy M(data loss) > M(incorrect) > M(delayed), e.g. 69 > 4 > 3. The old mapping (6, 4, 69) now fails.

Rule: many valid measures may exist (inch, cm, feet). The richer the empirical relation system, the fewer valid measures (more conditions to satisfy).

Measurement and models

A model strips unnecessary detail and shows one view (cost models show only cost factors). Forms: equations, mappings, diagrams. Every measure needs a model to explain how it is derived and how to read results.

LOC needs a program model: program vs subroutine? several statements on one line? comment lines? data declarations? different languages? versions on different platforms?

Defining attributes: don’t focus only on the maths. First identify the characteristics of the thing and a model that links them, then define measures. Bad examples: dog intelligence by IQ test.

McCabe cyclomatic number
V(G)=e−n+2=d+1

e = edges, n = nodes, d = decisions. = number of linearly independent paths. Slide graph: V(G) = 5.

Criticism: many programs with many decisions are still easy to understand → V(G) can mislead as a complexity measure.

Direct vs indirect measures

Direct: no other attribute needed. Height, mass, volume · LOC · test schedule (elapsed hours) · number of defects · months worked.

Indirect: combines measures, needs a model (density = mass / volume). Productivity = LOC / person-months · module defect density = defects / size · defect detection density = defects / total defects · requirements stability = initial reqs / total reqs · test effectiveness = items covered / total items · system spoilage = effort fixing faults / total effort.

Slides: raw fault counts per system area (direct) show 5 bad subsystems; fault density (indirect, faults/KLOC) shows area C2 (only 4 KLOC of 2 million) is the real headache.

Internal vs external

Internal: measured from the entity itself, without its behaviour (no execution needed). External: measured only through how it relates to its environment (behaviour matters).

External attributes are harder and measured late (reliability only after development). So we use internal ones to predict external ones (e.g. find error-prone modules at design time).

Goals of measurement research: find relationships between internal and external attributes; find new ways to measure attributes of interest directly.

Process measurement

Only 3 process attributes are directly measurable: duration, effort, number of incidents of a type. External process attributes are built from these.

  • AT&T inspections: cost = avg effort per KLOC reviewed; effectiveness = avg faults detected per KLOC.
  • Testing: track errors, duration and cost per sub-process (unit, integration, system, acceptance).
  • AI-assisted code review: direct = stage duration, effort per PR, model comments per PR; derived = defects per 1000 changed lines, comment precision (acted on / produced), cost per defect incl. inference.

Samples: development (elapsed time: days; milestones: dates; effort: staff-hours) · test (volume: tests scheduled; progress: tests executed / passed).

Product & resource measurement

Product = any artifact, not only deliverables. External product attributes need environment (reliability depends on machine and usage mode). Others: usability, integrity, efficiency, testability, reusability, portability, interoperability.

Product samples: system size (modules, DFD bubbles, function points, physical SLOC, memory), defect density (defects/KLOC, defects/FP), module length (physical SLOC, logical statements).

Resources measured for magnitude (how many staff?), cost (tool price?), quality (designer experience?).

Resource samples: staff (team size, years of domain / programming experience), time (start/due dates, elapsed days).

Empirical investigation

File 05 (labelled “Chapter 4 – Empirical investigation”)

Goal: apply the scientific method to SE. Empirical studies do not prove a theory; they give evidence to support or refute it, using a sample of all possible values.

Exploratory (qualitative)

In-depth understanding via interviews, observation. E.g. key factors of successful projects; sources of variation between inspection groups.

Explanatory (quantitative)

Quantify a relationship or compare groups to find cause–effect. Numbers allow statistics and hypothesis testing. E.g. which testing method is more effective? how much does a new inspection method cut faults found in test?

Key design principles: level of control (decides study type) · goals and hypotheses · control of variables · threats to validity · human subjects.

Three study types

Experimentresearch in the small
high control
Case studyresearch in the typical

Surveyresearch in the large

  • Controlled experiment: test well-defined hypotheses about independent → dependent variables while minimising other factors. Planned in advance. Rare in industry (too many confounding factors); common in academia.
  • Quasi-experiment (observational / natural experiment): cannot randomly assign subjects, often because the independent variable is a quality of the participant (gender, developer experience). Most SE case studies are really quasi-experiments.
  • Case study: identify key factors, document inputs, constraints, resources, outputs of an activity. Planned or retrospective.
  • Survey: retrospective (after the event). Record and compare; you cannot manipulate variables. E.g. after the first agile project, collect size, effort, faults, duration and compare to older projects.

Choosing a technique: 4 guidelines

Retrospective? Already happened → survey or case study. Not yet → case study or experiment
Level of control high → experiment; low → case study (also when control is too costly or risky, e.g. safety-critical)
Replication possible? No (can’t build the same project in each language) → case study
Cost of replication low → experiment

Experiments are considered more effective because results are usually more generalizable.

Hypotheses

  • State the hypothesis in quantifiable terms with independent and dependent variables. “Scrum gives better quality than XP” is not testable → “Scrum code has fewer defects per KLOC than XP code” is.
  • Quantifying uses surrogate measures (defects for quality, LOC for effort). Danger: a change in the surrogate may not equal a change in the real factor (many defects found = thorough testing or sloppy development). A bad quality measure threatens construct validity.
  • Null hypothesis H0: no relationship (no difference in defects/KLOC between Scrum and XP). Reject only with strong evidence, e.g. < 5% chance of no difference.
  • Only after rejecting H0, test alternatives: HA1 Scrum has fewer defects/KLOC; HA2 XP has fewer.

Control of variables

State variable (= independent variable): characterizes the project and can affect results (application area, system type, developer experience). Dependent variable: changes when independent variables change.

Experiment → sample OVER the state variable: cover many values (projects in as many languages as possible).
Case study → sample FROM the state variable: pick the typical value (the language most projects use).

Example: C = control language, Java = experimental; keep all other state variables equal so productivity differences come from language. NASA Goddard (FORTRAN → Ada): Ada productivity did not beat FORTRAN until the third use of Ada. No control over who uses which method (subject selection) → case study. Manipulation can be in a “toy” setting or a “field” setting.

Human subjects

US HHS (45 CFR 46.102(d)): a living individual about whom a researcher obtains (1) data through intervention or interaction, or (2) identifiable private information. SE risks are mostly privacy (reputation from being in the high-defect group, leaked private data). An IRB must approve: protections such as encrypting and destroying identifying data, and the study must be likely to have impact.

Paths from S to a root: S→R→P (length 2), S→Q (length 1). DIT = max = 2. Ancestors = R, P, Q → NAC = 3.

WMC = 1 + 3 + 2 + 4 = 10. With unity weights WMC = n = 4. NLM = 4 methods. CMC = 10 independent paths (unit of McCabe).

Q8LCOM2 weakness

Class X: m1{a}, m2{a}, m3{b}. Class Y: m1{a,b}, m2{b,c}, m3{c,a}. Compute LCOM2 for both. What does this show?

Answer

X: Q = {(m1,m2)} = 1, P = 2 → LCOM2 = 1.

Y: every pair shares something → Q = 3, P = 0 → max(0 − 3, 0) = 0.

(c) Ratio M = 2,5,10. Valid? R1 = 6,15,30 · R2 = 3,6,11.

Answer

(a) M1 ✓, M2 ✓ (order kept) · M3 ✗ (merges two classes) · M4 ✗ (order reversed).
(b) N1 ✓ (a = 2, b = 5) · N2 ✗ (gaps 30 and 50).
(c) R1 ✓ (a = 3) · R2 ✗ (that is M + 1; ratios change: 5/2 ≠ 6/3).

Q24mean vs median

Scale: trivial 1, simple 2, moderate 3, complex 4, incomprehensible 5. Team A: simple, moderate, moderate, complex, complex. Team B: trivial, trivial, simple, moderate, incomprehensible. Compute mean and median. Then recode incomprehensible = 10 and recompute. Which statistic should you report?

Answer

Original: mean A = 16/5 = 3.2, mean B = 12/5 = 2.4 · median A = 3, median B = 2.
Recoded: mean A = 3.2, mean B = 17/5 = 3.4 → the means flip; medians stay 3 and 2.
Report the median: the scale is ordinal, so the mean is not meaningful.

Q34hypotheses

Make this testable and write H0, HA1, HA2: “Pair programming produces better code than solo programming.”

Answer

Testable: pair-programmed code has fewer defects per KLOC than solo code.
H0: no difference in defects/KLOC between pair and solo code.
HA1: pair code has fewer defects/KLOC. HA2: solo code has fewer defects/KLOC.
Reject H0 only with strong evidence (e.g. p < 0.05). Defects/KLOC is a surrogate for quality.
